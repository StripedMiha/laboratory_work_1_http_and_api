# Workshop: клиент для SampleAPIs Coffee

Команда подключает офисную кофемашину к внешнему каталогу напитков. У поставщика есть публичный HTTP API — перед интеграцией нужно самостоятельно исследовать его поведение и написать Python-клиент.

**API:** [SampleAPIs Coffee](https://sampleapis.com/api-list/coffee)  
**Базовый URL коллекции:** `https://api.sampleapis.com/coffee/hot`

Формат: группы по 4–5 человек, общий результат — запускаемая программа и защита решения.

---

## Как начать

1. Сделайте **fork** репозитория и клонируйте свой fork:
   ```bash
   git clone <адрес-вашего-fork>
   cd laboratory_work_1_http_and_api
   ```
2. Создайте окружение и установите зависимости:
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   ```
3. Реализуйте:
  - методы клиента в `src/app/client.py`;
  - сценарий в `src/app/main.py`;
  - описание POST-запроса в module docstring файла `client.py`.
4. Проверьте клиента тестами:
  ```bash
   pytest
  ```
   Стартовый код — заглушки (`NotImplementedError`). Сначала большинство тестов **красные**, после реализации клиента — **зелёные**.  
   Два теста про `__init__` могут проходить сразу — это нормально.
5. Запустите сценарий:
  ```bash
   PYTHONPATH=src python -m app.main
  ```
   Если публичный API недоступен, поднимите мок и укажите его URL в клиенте:
   ```bash
   python mock_server/server.py
   ```
   В другом терминале создайте клиент с `base_url="http://127.0.0.1:8000/coffee/hot"`.

API публичный и общий. Работайте **только со своей** записью (по `id` из ответа POST) и удалите её в конце.

## Цель

Клиент должен уметь:


| Операция                | Метод HTTP | Метод клиента                      |
| ----------------------- | ---------- | ---------------------------------- |
| Список горячих напитков | GET        | `list_drinks()`                    |
| Напиток по id           | GET        | `get_drink(drink_id)`              |
| Создать запись          | POST       | `create_drink(payload)`            |
| Полная замена           | PUT        | `replace_drink(drink_id, payload)` |
| Частичное изменение     | PATCH      | `update_drink(drink_id, changes)`  |
| Удаление                | DELETE     | `delete_drink(drink_id)`           |


Общую HTTP-логику вынесите в `_request()`. Без `requests.Session()`.  
Базовый URL и тайм-аут задаются в конструкторе и **не дублируются** в каждом методе.

## Сценарий в `main()`

Каркас уже есть в `src/app/main.py` (`marker`, `created_id`, обработка ошибок, `finally` с очисткой). Нужно заполнить этапы:

1. Получить список горячих напитков.
2. Создать новый напиток с **уникальной меткой группы** (`marker` уже генерируется — добавьте её в название).
3. Сразу сохранить `id` из ответа POST в `created_id`.
4. Получить созданный напиток по id и сравнить поля с отправленными.
5. Полностью заменить данные через PUT → повторный GET (все заменённые поля).
6. Изменить часть данных через PATCH → повторный GET (изменённое поле обновилось, остальные сохранились).
7. Удалить напиток → GET по тому же id → обработать ожидаемый **404**.
8. После подтверждения удаления: `created_id = None`.

Даже если сценарий упал с ошибкой, программа в `finally` должна попытаться удалить запись, если `id` известен.

**После тайм-аута POST** результат создания может быть неизвестен: сообщите об этом и сохраните уникальную метку для ручной проверки. **Не повторяйте POST автоматически.**

## Требования к программе

- запросы через библиотеку `requests`;
- тайм-аут на **каждый** запрос;
- проверка HTTP-статуса **до** использования тела ответа;
- проверка JSON `Content-Type`;
- не вызывать `.json()` для ответа без JSON-тела;
- различать отсутствие ресурса (`CoffeeNotFoundError`) и остальные ошибки API (`CoffeeApiError`);
- не завершаться необработанным исключением в ожидаемых сценариях;
- использовать `id`, возвращённый POST;
- удалять созданную запись в конце;
- понятный вывод этапов в консоль.

Retry в рамках workshop **не реализуется** (в том числе для GET).

Расширенная локальная валидация (непустые строки, состав `ingredients` и т.п.) — по желанию.

## Описание запроса создания кофе

В module docstring `src/app/client.py` опишите в свободном формате:

- HTTP-метод и URL;
- необходимые заголовки;
- параметры JSON-тела: тип, обязательные / необязательные, ограничения на значения;
- какие поля задаёт клиент, какие создаёт сервер;
- ожидаемый успешный статус и форму ответа;
- какие правила подтверждены запросами к API, а какие проверяете только в клиенте.

OpenAPI / JSON Schema не нужны. Достаточно списка, короткого текста или компактной таблицы.

## Тесты (проверка себя)


| Что запускать                                   | Что это                                 | Ожидание до реализации клиента            |
| ----------------------------------------------- | --------------------------------------- | ----------------------------------------- |
| `pytest`                                        | тесты **вашего** клиента в `src/tests/` | почти все красные (`NotImplementedError`) |
| `python -m unittest discover -s mock_server -v` | тесты **самого** `mock_server`          | зелёные (к заданию клиента не относятся)  |


В `pytest` два набора:

- `src/tests/test_client.py` — unit через библиотеку `responses` (без сети);
- `src/tests/test_client_mock_server.py` — integration: поднимает локальный `mock_server`.

Покрывают контракт клиента: CRUD, тайм-аут, 404 → `CoffeeNotFoundError`, сеть/HTML/битый JSON → `CoffeeApiError`, DELETE с телом `{}`.  
Сценарий `main.py` тестами не покрыт — его проверяют запуском.

## Локальный мок (`mock_server/`)

Замена публичного API, если он недоступен, и способ показать сбои на защите:

```bash
python mock_server/server.py
python mock_server/server.py --fault GET=html
python mock_server/server.py --fault POST=slow --slow-seconds 15
python mock_server/server.py --fault DELETE=drop
```

В клиенте: `SampleApisCoffeeClient(base_url="http://127.0.0.1:8000/coffee/hot")`.  
Подробности — в `mock_server/README.md`.

## Критерии готовности

Решение принимается, если:

- [ ] программа запускается и выполняет основной сценарий;
- [ ] методы клиента соответствуют выданному интерфейсу;
- [ ] базовый URL и тайм-аут не дублируются в каждом методе;
- [ ] статусы и формат ответа проверяются корректно;
- [ ] ресурс создаётся, заменяется (PUT), изменяется (PATCH) и удаляется по своему id;
- [ ] ожидаемый 404 обрабатывается отдельно;
- [ ] группа не изменяет чужие записи;
- [ ] параметры POST описаны в docstring `client.py`;
- [ ] `pytest` по клиенту зелёный;
- [ ] группа может объяснить решение и ответить на вопрос преподавателя.
